# Blog Agent Protocol

> XBXyftx Hexo 博客项目的 Agent 主协议。
> `MEMORY.md` 负责导航，`rules.md` 负责硬性边界，本文负责任务生命周期、路由、证据和停止条件。

## 1. 角色边界

- 主 Agent 负责理解目标、确定范围、读取证据、决定是否调用 sub agent、修改文件、验证结果和请求授权。
- sub agent 是可选的只读上下文工具，只回答一个明确问题；它们不能直接修改博客源文件、提交、推送或部署。
- sub agent 的建议不是项目事实。主 Agent 必须回到当前源码、配置、生成结果或用户反馈核对关键结论。
- 不因任务涉及代码、主题文件或交付步骤就默认启动一组 sub agent。

## 2. 任务分类

开始任务时先记录最小上下文：

```text
任务类型：文章 / 页面 / 主题 / 脚本 / 配置 / 构建性能 / 部署 / Bug / 记忆维护 / 只读分析
目标：用户希望得到的可观察结果
范围：文件、目录、页面路由或功能入口
现有证据：源码、配置、Git diff、生成文件、日志、截图、用户反馈
写入范围：只读或允许修改的目录
授权状态：是否允许构建、提交、推送、部署或外部写操作
结束条件：什么事实或验证结果可以结束任务
```

### 不启动 sub agent

- 单文件的文案、颜色、尺寸、资源路径或 Markdown 格式调整，且不影响状态、路由、API 或数据流。
- 用户已经明确目标文件、改法和验收条件，没有历史不确定性、本地差异或跨模块影响。
- 只修复链接、front matter 字段、索引条目或提示词措辞。

### 按需启动 sub agent

| 问题信号 | 最小角色 | 仅在以下情况追加 |
| --- | --- | --- |
| 记忆入口或历史结论不清 | `memory-router` | 找到相关入口后停止 |
| 目标文件存在本地差异 | `workspace-guardian` | 只检查目标文件和 diff |
| 新页面行为、资源复用或调用关系不清 | `site-chain-mapper` | 发现跨模块影响后追加 `architecture-reviewer` |
| Hexo 生成链、主题模板或注入关系不清 | `render-chain-reviewer` | 涉及多个生成阶段或主题层时追加 |
| 有浏览器日志、构建日志或资源审计结果 | `evidence-analyzer` | 需要源码对应时追加链路角色 |
| 主题生命周期、PJAX、懒加载或性能影响 | `theme-runtime-reviewer` | 纯样式和静态资源替换跳过 |
| 改动需要多页面或多断点回归 | `verification-planner` | 影响面确认后再启动 |
| 修改多个长期记忆入口 | `handoff-summarizer` | 单行索引更新跳过 |

并行执行相互独立的只读角色。问题已经回答后立即停止；除非用户明确要求深度审查，最多追加一批角色。

## 3. 渐进式读取

所有任务先读取：

1. 根 `AGENTS.md`（工作区边界和授权规则）。
2. `long-term-memory/MEMORY.md`（项目事实和导航）。
3. `long-term-memory/rules.md`（硬性约束）。

然后按任务路由读取，不扫描整个记忆树：

| 任务 | 继续读取 |
| --- | --- |
| 新建或修改文章 | `02-requirements/README.md`、文章相邻 asset 目录、必要的渲染规范 |
| 修改自定义页面 | `02-custom-pages/` 对应文档、页面源文件和资源目录 |
| 修改 `scripts/` 或 `source/js/` | `03-api-practices/README.md`、对应脚本文档、生成数据契约 |
| 修改 Butterfly 主题 | `06-theme-modifications/README.md`、对应主题模板/资源、相关运行时文档 |
| 构建、资源或性能问题 | `03-api-practices/deployment-pipeline.md`、相关审计和验证工具说明 |
| 部署 | `03-api-practices/deployment-pipeline.md`、`部署.txt`、最近操作记录 |
| 已知异常 | `07-known-issues/README.md`、对应操作记录和证据 |
| 长期记忆维护 | `document-authoring-rules.md`、受影响分区 README 和条目 |

只有涉及 sub agent 编排或协议维护时，才需要再次展开阅读本文全部内容。

## 4. 博客专属事实边界

- `source/` 是内容源；`public/`、`.deploy_git/`、`db.json` 和自动生成 JSON 不是手工编辑的权威源。
- `scripts/` 会在 Hexo 生命周期中运行。`private-posts-scanner.js`、`birthday-gift-scanner.js` 和其他扫描器可能改写跟踪的生成数据，运行构建后必须重新检查 `git status`。
- `npm run webp` 及 `dev`、`opt`、`pub` 可能转换并删除源图；未经用户明确授权不得为了验证随意运行。
- `themes/butterfly/_config.yml` 是主题默认配置，禁止直接修改；项目定制集中在根配置、主题模板和主题资源的既有边界内。
- `source/coffer/` 只有客户端密码保护。它不能被描述为真正的服务端机密存储，也不能把敏感信息写入公开构建产物。
- 部署目标有 GitHub Pages 和私有服务器。没有明确授权不得执行 `npm run deploy`、`npm run pub`、Git push 或任何远程写操作。

## 5. 证据标签

写入长期记忆、操作记录或交接摘要时使用以下标签：

| 标签 | 含义 |
| --- | --- |
| `代码事实` | 当前源码、配置、文件存在性或 diff 直接证明 |
| `生成事实` | 本地构建、扫描器或审计工具实际产生的结果 |
| `历史结论` | 旧文档、旧 commit 或旧方案中的记录，仍需核对当前源码 |
| `用户/测试反馈` | 用户、浏览器、人工测试或外部系统提供的结果 |
| `推断` | 基于证据形成但尚未完全证明的解释 |
| `待确认` | 缺少源码、日志、网络、人工或设备证据 |
| `已验证` | 有明确且可复现的验证结果支持 |

提交记录只能证明某次变更存在，不能证明构建、浏览器、设备或部署已经通过。静态分析不能写成运行时验证，Agent 建议不能写成已加载工具或用户确认。

## 6. 执行与验证

修改前：

1. 检查目标仓库 `git status --short`，识别并保护既有差异。
2. 阅读目标文件及其分区入口，确认现有链路和生成数据契约。
3. 形成最小改动计划，并明确需要运行的检查。

修改后：

1. 检查 diff、`git diff --check`、临时诊断、链接和索引。
2. 若修改主题、脚本、配置或资源，按影响面选择静态检查、clean build、生成态审计或浏览器检查。
3. 把“已执行的检查”和“仍需人工/设备验证”分开记录。
4. 文档变更同步对应分区 README、`MEMORY.md` 或操作日志。

推荐的验证表达：

```text
已验证：执行了什么命令/检查，得到什么可复现结果。
待确认：还缺少什么人工、浏览器、设备、网络或部署证据。
无法验证：原因是什么，不能由当前结果推出什么结论。
```

## 7. 统一输出模板

主 Agent 或 sub agent 的调查结果按需使用以下顺序：

```text
适用性：适用 / 不适用；命中的问题信号
检查范围：检查了什么，明确排除了什么
代码事实：路径、入口、配置、调用关系和证据位置
历史结论：仍有效、已过时或与当前事实冲突的记录
风险与待确认：证据缺口、潜在影响和验证限制
建议下一步：主 Agent 需要执行的最小动作
停止原因：证据足够 / 不适用 / 外部证据缺失 / 达到范围边界
```

## 8. 记忆写入与交接

- 根索引只保留当前状态、导航和高价值结论；长日志、截图、完整审计放到对应分区或子目录。
- 每个主题、功能或操作只保留一个主要入口；入口膨胀时下沉证据，不复制整篇内容。
- 文章内容、主题实现、操作记录和已知问题分开维护，避免把一次性修改写成永久规则。
- 完成任务后更新交接快照：当前状态、已改文件、已验证内容、未决风险和下一步。
- 未经授权不提交、推送、部署、恢复、删除或覆盖文件。
