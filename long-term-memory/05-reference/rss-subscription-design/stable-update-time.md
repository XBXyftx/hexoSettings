# RSS 稳定内容更新时间

> 2026-10-10：已本地实现、测试和浏览器验证，未提交、未推送、未部署。用户同意 Git 历史基线加持久化内容哈希，不改文章 ID、发布日期。

## 实现边界

- `tools/lib/rss-update-state.js` 管理时间基线与台账；`rss-feed-policy.js` 在公开文章筛选之后调用它，仍复用 feed4 生成 XML。
- 不修改 node_modules、Hexo/Butterfly、全站 `updated_option`、文章 front matter 或正文。
- `.rss-feed-state.json` 位于项目根目录，由 `rss_subscription.state_path` 指定；不能放 source/public，不能忽略或当 clean 缓存删除。
- 台账需要随文章一起提交并同步到其他机器。本次生成了文件，但未执行 git add/commit/push。
- 仅记录公开、已到发布日期的文章，包括最近 30 条窗口之外的公开文章。字段为 source、SHA-256、ISO updated、basis、可选 source_commit，不记录正文或私密文章。

## 时间规则

1. 原 Markdown 显式包含有效 updated 时，沿用 Hexo 已解析的时区语义，作为作者覆盖。
2. 哈希和台账一致时复用时间，完全不读取文件 mtime。
3. 有台账但内容改变时，记录本次生成观察时间；不早于上一记录和发布日期。之后重复生成、仅提交同样内容不会推进时间。
4. 首次建档且文件与 HEAD 内容一致时，取该路径当前内容版本的 Git committer 时间；跳过仅改变 BOM、CRLF 或末尾空行的提交。提交时间是历史近似，不声称等于实际编辑时间。
5. 首次建档且有本地未提交修改或新文件时，取观察时间，不把旧 Git 时间赋给新内容。
6. 无 Git 历史且无匹配台账时，警告并以发布日期保守回退。浅克隆需要补全历史才能初始化新基线；已同步的匹配台账可以直接复用。

哈希包含完整原 Markdown（front matter 与正文），只规范化 BOM、换行符和末尾换行；不去除行内/行尾空格，保留 Markdown 语义。只换图片二进制、主题或公告不会改变文章源哈希。文件重命名不跟随旧路径台账，本期也不承诺跨重命名身份迁移。

显式 updated 是人工优先覆盖：作者若填了固定值，正文再次修改不会强行改掉它；普通文章无需填写该字段。

## 保存与失败

- 两种 XML 通过生成内校验后才保存台账；校验失败不写入。
- 保存使用同目录临时文件和 rename，避免半写 JSON；写入前比较原文件检测已发生的其他构建修改。仍要求串行构建，这不是多进程锁。
- 内容完全相同时不重写台账，clean 后仍保留。
- JSON 损坏、版本不支持、合并冲突、非法记录时停止，不静默用 mtime 重建。
- 台账记录的是“成功生成订阅时观察到的内容版本”，不是部署事务：后续其他生成器、落盘、postbuild 或远程发布失败不会回滚台账；同内容重试保留时间。
- 从生成结果中排除或删除的文章在下次成功生成时移出台账；重新公开时会重新建立基线。
- 台账丢失会失去未提交内容的观察历史，只能重新从 Git/发布日期建立近似基线；不要将其当临时缓存清理。

## 使用与迁移提示

日常命令仍是 pub；成功构建可能更新台账，后续源码提交时应一并审阅和同步，不能只推送 Markdown。内容相同但文件时间改变不会再造成全站伪更新。

首次发布本次修复会把原来受 mtime 污染的 updated 改回较早的 Git 时间，部分阅读器可能保留原缓存或不重标未读；不通过变更 ID 强制制造新文章。RSS 2.0 的 item 仍没有独立 updated，旧文提醒依旧由阅读器决定，30 篇窗口规则不变。

当前仅本地产物已修复，线上尚未更新。既有 HTML 文章页仍遵循全站 mtime 设置，若希望页面也改用稳定时间，应单独评估，不通过修改共享 Post 模型偷偷扩大范围。
